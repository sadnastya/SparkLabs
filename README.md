# SparkLabs — лабораторная 1

Запуск Apache Spark локально в Docker и вычисление N-го числа Фибоначчи
приложением на Java в режиме `--deploy-mode client`.



## Алгоритм

### Почему Фибоначчи решается матрицами

Один шаг рекуррентности — это умножение вектора на постоянную матрицу. Возьмём
вектор из двух соседних чисел и распишем, что должно получиться на следующем шаге:

```
 [F(n+1)]   [1  1]   [F(n)  ]          F(n+1) = 1·F(n) + 1·F(n-1)   <- сама рекуррентность
 [F(n)  ] = [1  0] · [F(n-1)]          F(n)   = 1·F(n) + 0·F(n-1)   <- сдвиг окна
```

Матрица M = [[1,1],[1,0]] не зависит от n, то есть каждый шаг — это одно и то же
умножение. Значит n шагов подряд — это n умножений на ту же матрицу:

```
 [F(n+1)]        [F(1)]        [1]
 [F(n)  ] = M^n · [F(0)] = M^n ·[0]
```

Отсюда замкнутая форма, которую легко проверить по индукции:

```
        [F(n+1)  F(n)  ]
 M^n =  [F(n)    F(n-1)]
```

Иными словами, **возведение M в степень n — это и есть n шагов рекуррентности,
выполненных разом**. Подстановка n=1 даёт саму M, а переход n -> n+1 — это ровно
одно домножение на M. Первые степени (числа из реального прогона):

| n | M^n | F(n) = элемент [0][1] |
|---|---|---|
| 1 | `[[1,1],[1,0]]` | 1 |
| 2 | `[[2,1],[1,1]]` | 1 |
| 3 | `[[3,2],[2,1]]` | 2 |
| 4 | `[[5,3],[3,2]]` | 3 |
| 5 | `[[8,5],[5,3]]` | 5 |
| 6 | `[[13,8],[8,5]]` | 8 |

Код берёт именно элемент `[0][1]`: `return power[1]` в `FibonacciApp.fibonacci`.

### Как это ложится на Spark

Исходная запись F(n) = F(n-1) + F(n-2) для Spark бесполезна: чтобы посчитать
элемент, нужно уже знать предыдущий, распараллеливать нечего. А вот запись через
степень — это произведение n **одинаковых и независимых** сомножителей:

```
 M^n = M · M · M · ... · M        (n штук)
```

Умножение матриц ассоциативно, поэтому скобки можно расставлять как угодно:

```
 M·M·M·M·M·M·M·M·M·M  =  (M·M) · (M·M·M) · (M·M) · (M·M·M)
       10 штук                 разложено по 4 партициям
```

Это в точности контракт `rdd.reduce(f)`. Что происходит при `N=10, partitions=4`:

1. `sc.parallelize(factors, 4)` режет список из 10 матриц на партиции по 2, 3, 2, 3
   элемента и раздаёт их экзекьюторам.
2. Каждый экзекьютор независимо сворачивает свою партицию своим `multiply`:
   получаются частичные произведения `M^2`, `M^3`, `M^2`, `M^3`.
3. Частичные результаты уезжают на драйвер, и он домножает их друг на друга:
   M^2 · M^3 · M^2 · M^3 = M^10 = `[[89,55],[55,34]]`, то есть F(10) = 55.

Сетью при этом гоняются четыре матрицы 2x2, а не десять — сворачивание происходит
на месте, у данных.

### Две оговорки, важные для корректности

**Коммутативность.** Документация Spark требует от `reduce` оператора не только
ассоциативного, но и коммутативного: драйвер домножает частичные результаты в том
порядке, в каком таски завершились, а не в порядке партиций. Умножение матриц в
общем случае некоммутативно, и это был бы баг. Здесь его нет, потому что все
сомножители — одна и та же матрица M: любые её степени перестановочны,
M^a · M^b = M^b · M^a = M^(a+b). Для разных матриц пришлось бы сохранять порядок
через `zipWithIndex` и `fold` вместо `reduce`.

**Сложность.** Всего по-прежнему выполняется n умножений — быстрое возведение в
степень (O(log n)) здесь намеренно не используется, иначе распределять было бы
нечего. Это учебная демонстрация распределённой свёртки ассоциативной операции,
а не самый быстрый способ получить F(n): на одной машине алгоритм fast doubling
посчитает то же самое за log n шагов. Плюс с ростом n растут сами числа, поэтому
одно умножение `BigInteger` дорожает, и ускорение от партиций не линейное.

Числа хранятся в `BigInteger`: `long` переполняется уже на F(93).

## Код: что выполняется на драйвере, а что на экзекьюторе

### Границу проводит единственный action

Почти весь код `FibonacciApp` — драйверный. На экзекьюторы уезжает ровно один
фрагмент: тело `multiply`, и только в момент выполнения `reduce`.

| Фрагмент | Строки | Где выполняется |
|---|---|---|
| разбор `args`, валидация `n` | 36-47 | драйвер |
| `new SparkConf()` | 49 | драйвер |
| `new JavaSparkContext(conf)` | 51 | драйвер: поднимает UI на :4040, регистрирует приложение у мастера, получает экзекьюторы |
| сборка `List<BigInteger[]> factors` | 86-89 | драйвер, в его куче |
| `sc.parallelize(factors, partitions)` | 90 | драйвер: данные пока никуда не уехали, создан только план (`ParallelCollectionRDD`) |
| **`rdd.reduce(FibonacciApp::multiply)`** | 91 | **точка перехода**: планирование на драйвере, свёртка партиций на экзекьюторах, объединение частичных результатов снова на драйвере |
| `multiply` | 96 | **и там, и там** |
| печать результата | 61-70 | драйвер, поэтому вывод виден в вашем терминале |
| `Thread.sleep(HOLD_SECONDS)` | 73 | драйвер |
| выход из try-with-resources | 74 | драйвер: закрывает контекст, экзекьюторы гасятся, :4040 пропадает |

`parallelize` и `reduce` в соседних строках — это не две операции одного типа.
`parallelize` — трансформация, она ленивая и ничего не считает. `reduce` —
единственный action, и именно он запускает job. Отсюда и `n` в логе:

```
INFO SparkContext: Starting job: reduce at FibonacciApp.java:91
INFO DAGScheduler: Got job 0 ... with 4 output partitions
INFO DAGScheduler: Submitting 4 missing tasks from ResultStage 0 (ParallelCollectionRDD[0] ...)
```

Стадия одна, шаффла нет: свёртка не требует перераспределения данных между
экзекьюторами.

### Что физически уезжает по сети

**Jar.** Драйвер поднимает файловый сервер и раздаёт собранный jar экзекьюторам:

```
INFO SparkContext: Added JAR file:/.../target/spark-labs.jar
                   at spark://192.168.0.105:43305/jars/spark-labs.jar
```

Экзекьютор скачивает его и добавляет в свой classpath — так класс `FibonacciApp`
оказывается доступен на той стороне. Именно поэтому важна версия байткода:
грузить его будет JDK 17 из контейнера.

**Таск вместе с данными.** У `parallelize` источник данных — коллекция в куче
драйвера, поэтому элементы партиции сериализуются прямо в тело таска:

```
INFO TaskSetManager: Starting task 0.0 in stage 0.0 (TID 0)
                     (127.0.0.1, executor 0, partition 0, PROCESS_LOCAL, 10364 bytes)
```

10 КБ на таск — это те самые 50 матриц (при `N=200, partitions=4`) плюс описание
вычисления. Обратно возвращаются четыре матрицы 2x2 — частичные произведения.

**Функция.** Ссылка `FibonacciApp::multiply` сериализуется как объект лямбды. Он
пустой: кода в нём нет, есть лишь указание «вызвать статический метод
`multiply` класса `ru.sparklabs.FibonacciApp`». Сам байткод берётся из jar,
который уже уехал первым пунктом.



## Запуск

```bash
# 1. Поднять кластер
docker compose up -d
curl -s http://localhost:8080/json/ | head    # master ALIVE, aliveworkers: 1

# 2. Собрать jar
JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64 \
  mvn -s .mvn/settings-central.xml clean package

# 3. Получить локальный spark-submit той же версии, что и кластер
cid=$(docker create apache/spark:4.0.1) && docker cp "$cid":/opt/spark ./spark-dist && docker rm "$cid"

# 4. Локальная проверка логики
JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64 ./spark-dist/bin/spark-submit \
  --master 'local[*]' --class ru.sparklabs.FibonacciApp target/spark-labs.jar 50

# 5. Целевой запуск: client mode на кластере
#    Аргументы приложения: <N> [partitions]

JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64 ./spark-dist/bin/spark-submit \
  --master spark://127.0.0.1:7077 \
  --deploy-mode client \
  --class ru.sparklabs.FibonacciApp \
  --executor-memory 1g \
  --total-executor-cores 2 \
  target/spark-labs.jar 200 4

# Остановить кластер
docker compose down
```


## Про сеть

`network_mode: host` в compose выбран потому, что в client mode executors обязаны
открыть обратное соединение к драйверу на хосте. На Linux host-сеть снимает
необходимость пробрасывать порты драйвера.

# Лабораторная 3 — шаблон приложения

Шаблон: `src/main/java/ru/sparklabs/lab3/Lab3App.java`. Свою логику писать в методе
`run` (сейчас там пример-заглушка на `spark.range`).

Запуск целиком в Docker — локальные `spark-dist` и JDK для запуска не нужны,
драйвер стартует в одноразовом контейнере `spark-submit` (client mode):

```bash
# 1. Поднять кластер (master + worker)
docker compose up -d

# 2. Собрать jar — каталог target/ монтируется в контейнер как /opt/app
mvn -s .mvn/settings-central.xml clean package

# 3. Запустить Lab3App на кластере
docker compose run --rm spark-submit

# То же с аргументами приложения или другим классом:
docker compose run --rm spark-submit \
  --class ru.sparklabs.lab3.Lab3App /opt/app/spark-labs.jar 5000000
```

После правок кода достаточно повторить шаги 2 и 3. Пока приложение работает,
Spark UI драйвера доступен на http://localhost:4040, мастер — на http://localhost:8080.
